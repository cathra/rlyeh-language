## 1. 背景与动机

用户明确：**TCL2 = ISO 26262-8（道路车辆功能安全）中的"工具置信度等级 2"（Tool Confidence Level 2）**，用于判断"开发工具（编译器/运行时）出 bug 会不会害到车规安全相关软件"。

因此本计划的目标**不是**把"用 Rlyeh 写的软件"认证为车规安全，而是把 **Rlyeh 这套开发工具本身** 鉴认为 ISO 26262-8 下的 TCL2 工具——即：提供足够证据，证明 Rlyeh 即便有缺陷，其缺陷被引入安全相关软件、并逃逸到最终产品的**风险足够低**，从而无需按完整安全生命周期开发工具（那是 TCL3）。

Rlyeh 的设计（分层内存、零 GC 默认、Actor 隔离、编译期确定性、可差分对拍）天然有利于降低"工具影响（TD）"与提升"错误检测置信"，但当前缺少：**TD 分析、资质测试套件、使用历史/缺陷追踪、工具资质报告（TQR）与配置/变更管理**。本 RFC 据此给出分阶段优化计划。

## 2. ISO 26262-8 方法学（要求基线）

ISO 26262-8:2018 §11「软件工具资质」规定：

### 2.1 工具置信度等级（TCL）的判定
两个因素决定 TCL：

- **TD（Tool Impact，工具影响）**：
  - **TI**：工具结果**可违反**安全相关项的安全要求 → 高影响；
  - **TnI**：工具结果**不会**违反安全要求 → 无高影响。
- **错误避免/检测的置信**（考虑使用上下文，靠工具自身或流程其他手段达成）。

| TD | 错误避免/检测置信 | TCL |
|----|------------------|-----|
| TnI | — | 1（通常无需资质） |
| TI  | 高置信（工具自身或流程其他手段可检测） | 1 |
| TI  | 低/中置信 | 2 或 3 |

### 2.2 资质方法（qualification methods，ISO 26262-8 方法代码 1a/1b/1c）
| 方法（代码） | 适用 TCL | 含义 |
|------|----------|------|
| 提高使用置信（**1a** confidence from use） | 1 / 2 | 现场经验、使用历史、已知错误分析 |
| 评估资质（**1b** qualification by evaluation） | 1 / 2 | 执行测试用例 / 评估工具行为 |
| 按安全标准开发（**1c** qualification by development） | 3 | 工具本身按 ISO 26262 安全生命周期开发（需求/架构/验证/确认） |

**ASIL 与资质方法的对应**（ISO 26262-8 工具资质表）：不论 ASIL A–D，**TCL2 均经方法 1b（评估）达标，辅以 1a（使用置信）**；仅当需 TCL3 时才走 1c（完整开发）。即 ASIL 等级影响所需**证据强度**，不改变 TCL2 的方法选择。

> **本 RFC 目标**：Rlyeh 走 **TCL2** → 主路径 **方法 1b（评估资质）**，辅以 **1a（提高使用置信）**；不走 1c（TCL3 完整安全生命周期开发）。目标 ASIL = **B + C**（见 §8 开放问题 1）。

### 2.3 对 Rlyeh 的映射（基线假设）
- **TI 候选**：`rlyeh-codegen`（LLVM 后端、注入内建）、`rlyeh-typecheck`/`borrowck`/`regionck`（错误放行→生成不安全代码）、`rlyeh-region-alloc`/`gc-runtime`（运行时内存错误）。
- **TnI 候选**：`rlyeh-doc`、`rlyeh-fmt`、`rlyeh-bench`、纯文档/格式化输出。
- **错误检测手段（提升置信的核心）**：Rlyeh 自身的内存安全特性（消除 UB）+ `rlyeh-check` MISRA 类 lint + 差分/对拍 + 代码评审 + 在目标硬件上的测试。

## 3. Rlyeh 现状能力盘点（对 TCL2 的贡献度）

| 能力 | 现状 | 对 TCL2 的作用 |
|------|------|----------------|
| 分层内存 L0–L3 | ✅ 全部实现 | 降低 TD：生成代码本身内存安全，减少工具缺陷的下游危害 |
| 静态所有权 + 借用检查 | ✅ 但**宽松模式**（G1） | 双刃：减少生成 UB，但宽松可能漏检→需证明/收紧 |
| 区域系统（零开销批量释放） | ✅ 已实现 + 运行时接线 | 降低 TD（批量释放无悬垂窗口） |
| `unsafe`/裸指针/`repr(C)`/FFI 门禁 | ✅ 0.2.0-E | 需**审计 unsafe 契约**（TD 收敛） |
| Actor 隔离 | ✅ 邮箱 FIFO 互斥 | 降低 TD（并发无数据竞争） |
| `const`/`static` 确定性 | ✅ 0.2.0-V | 提升错误检测置信（可复现/可差分） |
| 数组/切片边界检查 | 🟢 已硬化（MVP）：Vec/`String`/`&str`/切片 `arr[i]`/`arr[i]=v` 经 `rlyeh-codegen` 注入越界 → `call @abort()` 确定性中止（IR + 运行时验证）；裸指针/`Str`/固定数组越界仍无检查（待补） | 已落地（eh-8 M4） |
| 整数溢出语义 | ❌ **未定义/未检查** | TD 风险源（见 §5.2） |
| UB 清单 | ❌ 无 | 资质证据缺口（见 §5.1） |
| 差分/对拍 harness | 🟠 M-M1 lexer 对拍已建，可扩展 | 评估资质核心手段（见 §5.3） |
| 回归套件 | ✅ 全量 253/255/330 通过 | 「使用置信」基础证据（见 §5.4） |
| 形式化语义 | ❌ 无 | 长期可提升置信，非 TCL2 必须 |
| 静态分析 `rlyeh-check` | 🟠 基础 lint | 需升级为认证级（见 §5.2） |
| 缺陷追踪/配置管理 | ❌ 无专门资质流程 | 资质流程缺口（见 §5.5/§5.6） |

## 4. 差距分析（Gap → TCL2）

| 维度 | 当前缺口 | 风险 |
|------|----------|------|
| TD 分析 | 无 TI/TnI 清单与影响面收敛 | 🔴 高（资质起点缺失） |
| 错误检测置信 | 溢出未定义、UB 清单缺、`rlyeh-check` 仅基础（注：直接 `arr[i]` 越界已硬化，见 §5.2） | 🔴 高 |
| 评估资质测试 | 仅 lexer 对拍 + 回归，缺规范符合性/codegen 差分/模糊测试 | 🔴 高 |
| 使用置信证据 | 无缺陷追踪/变更/版本资质记录 | 🟠 中 |
| 资质文档 | 无 TQR/安全手册/配置管理 | 🟠 中 |
| 形式化 | 非 TCL2 必须，但可加分 | 🟡 低 |

## 5. 优化/资质计划（里程碑）

### 5.1 TD 分析与影响面收敛（qualification 起点）
- 产出 **`docs/tool-impact-analysis.md`**：枚举各 crate 输出，标注 TI/TnI 与危害场景（codegen 误编译、typecheck 漏检、区域/GC 运行时错误）。
- 收敛 TI 面：审计 `unsafe` 契约（0.2.0-E）、最小化注入内建的信任边界、对 codegen 关键路径做独立评审。

### 5.2 错误检测置信提升（把"语言安全特性"转为检测手段）
- **UB 清单 + 防御**：`docs/ub-inventory.md`，枚举 UB 来源并标注防护（静态拒绝/运行期 trap/文档豁免）。
- **整数溢出语义**（高优先）：明确默认策略（认证/调试构建 panic，发布可配 wrap 且文档化），消除 std 内部"未检查"路径（涉及 `rlyeh-codegen` + `rlyeh-std`）。
- **边界检查全覆**（✅ 已落地 MVP，eh-8 M4，2026-09-20）：Vec/`String`/`&str`/切片的直接 `arr[i]`/`arr[i]=v` 越界已注入 `call @abort()` 确定性中止（IR + 运行时验证，见 `tests/run-pass/vec_index_inbounds.rl`）；区间/切片检查与裸指针解引用约束待补。
- **未初始化读防护**：栈槽默认零初始化或借用检查兜底。
- **MISRA 类 lint（升级 `rlyeh-check`）**：危险隐式转换、指针别名限制、动态内存约束、函数纯度（`pure fn`）、禁止丢弃返回值——产出认证级规则 + 豁免清单。
- **确定性**：safe 子集禁止非确定性（`clock`/`random`/调度敏感）；落实 `comptime.md` 的 hermetic 约束（确定性、可缓存、可对拍）。

> 上述每一项既降低 TD，又提高"错误检测置信"，直接把 TCL 推向 1/2。

### 5.3 评估资质测试套件（qualification by evaluation 核心）
- **差分/对拍**：扩展 M-M1 harness 到 codegen（Rlyeh 输出 vs 参考行为/oracle），覆盖溢出/边界/确定性。
- **规范符合性套件**：以 `semantics.md`/`grammar.md` 为基准的可执行规范测试。
- **回归基线**：固化 253/255/330 套件为资质回归（每次变更须全绿）。
- **模糊测试**：AFL/libFuzzer + Sanitizer 对编译器/运行时做无 UB 模糊，证明缺陷注入被捕获。
- **在目标硬件测试**：生成代码在目标 MCU/ECU 上的行为验证（车规语境的最终检测层）。

### 5.4 使用置信证据（confidence from use）
- **现场经验日志**：记录真实项目使用、已知缺陷与修复（含 0.2.0 自举前的能力落地史）。
- **缺陷追踪与变更管理**：建立工具缺陷登记、影响评估、回归闭环。
- **版本/配置管理**：编译器版本、标准库版本、目标平台三元组的资质绑定。

### 5.5 资质文档包
- **工具资质报告（TQR）**：TD 分析 + 资质方法选择 + 测试证据 + 结论。
- **安全手册**：内存模型、UB 清单、确定性约束、`unsafe` 审计、资质使用边界。
- **资质计划（Qualification Plan）**：明确 TCL 目标、适用 ASIL、方法、责任。

### 5.6 流程与持续维持
- 配置管理（CM）：工具、标准库、目标的版本锁定与发布门禁。
- 变更控制：每次工具变更触发资质回归（§5.3），确保 TCL2 持续有效。

## 6. 与 0.2.0 / 0.3.0 的关系

- **0.2.0-E `unsafe` 已完成**：审计其契约即 §5.1 的 TD 收敛输入。
- **0.2.0-V `const` 确定性已完成**：§5.2 确定性的地基。
- **0.3.0 自举**反向赋能：自举编译器本身受资质约束，其运行历史即 §5.4 的"使用置信"证据；`comptime.md` 的 CTFE hermetic 约束同时满足 §5.2 确定性。

## 7. 验证与证据（qualification 验收）

- **评估资质**：§5.3 套件全绿（差分对拍、规范符合性、模糊无 UB、目标硬件测试）。
- **错误检测置信**：`rlyeh-check` 认证级 lint 全绿 + `unsafe` 审计零未记录项 + UB 清单闭环。
- **使用置信**：缺陷追踪齐备、至少一轮"现场经验/使用历史"归档。
- **文档**：TQR + 安全手册 + 资质计划通过评审。

## 8. 风险与开放问题

1. **目标 ASIL 等级（已确认：ASIL B + C）**：用户以"1b + 1c"表述，已明确为 **ASIL B 与 ASIL C**（非 ISO 26262-8 的资质方法代码 1b/1c）。B/C 对 TCL2 的启示：**TCL2 经方法 1b（评估）即可达标，无需 TCL3/1c**；ASIL C 比 B 的证据强度要求更严，但同走 1b 路径。→ **§5.3 评估套件与 §5.4 使用置信为达标核心交付物**，ASIL C 项需更高的测试覆盖与评审深度。
2. **codegen 是否可达 TnI / 高检测置信**：基于 LLVM 的后端难以形式证明，可能必须靠 §5.3 评估测试覆盖来达成 TCL2（而非 TCL1）。
3. **TCL1 vs TCL2 边界**：若能通过流程内检测手段（§5.2 lint + 评审 + 目标测试）论证"高检测置信"，可争取 **TCL1**（成本更低）；本 RFC 以 TCL2 为保守目标。
4. **TCL3 长期选项**：若客户要求，可评估"按 ISO 26262 开发工具"（完整安全生命周期），但成本极高，超出本计划范围。
5. **直接下标 `arr[i]` 边界检查**现状须先确认（决定 §5.2 硬化范围）。

## P1. Poller kqueue 分派（LD#7，低风险，独立优先）

- **目标**：`io/nio.rl` 的 `Poller` 加 `kq: i64` 字段，`new`/`register`/`deregister`/`poll` 按 `__rlyeh_target_os()` 分派 kqueue（macOS/BSD 码 2/4）vs poll(2) 兜底（其他平台）。
- **前置**：无（`__rlyeh_kqueue`/`__rlyeh_kevent` 平台注入已就绪，`y2b_kqueue_wait.rl` 已验证）。
- **波及**：`io/nio.rl`（Poller struct + 四方法）；`future.rl`/chatd/smoke 调用签名不变，无需迁移；新增 Poller 集成测试。
- **步骤**：
  1. `Poller` struct 加 `kq: i64`（非 macOS/BSD 置 -1 触发兜底）
  2. `new`：macOS/BSD 调 `kqueue_new()`；`register` = `kevent_ctl(EV_ADD)`；`deregister` = EV_DELETE；`poll` = `kevent_wait` 解析 eventlist
  3. 其他平台保留现有 poll(2) 实现；WASI 短路保留
  4. 新增集成测试（socketpair 就绪事件经 Poller 分派）
- **验收**：macOS 下 `Poller` 事件等待正确；Linux/兜底平台回归全绿；166 用例 + 新增全过。

## P2. json::parse 严格校验 + `try_parse`（PR#1，中风险）

- **目标**：新增 `json::try_parse::<T>(s) -> Result<T, JsonError>`（严格校验，非法输入 `Err`）；`parse`/`from_str` 退化为 `try_parse(...).unwrap()`（向后兼容，现有调用点无需迁移）。
- **前置**：P1 无关。需先新增 `core.rl` 严格校验 helper。
- **步骤**：
  1. `core.rl` 新增 `parse_int_strict(s) -> Result<i64, String>`（全数字 + 可选负号校验）与 `json_unescape_checked(s) -> Result<String, String>`（引号闭合 + 转义校验）；166 用例回归
  2. `call.rs` + `json.rs` 新增 `check_json_try_parse` 入口（返回 `Result<T, JsonError>`）
  3. 各分支注入校验：i64 用 `parse_int_strict`；bool 三态（true/false/其余 Err）；String 用 `json_unescape_checked`；HashMap/struct 首尾 `{}` 闭合 + `find(":")` 失败 → Err
  4. `json::parse`/`from_str` 内部退化为 `try_parse(...).unwrap()`；`json::from_reader` 调用链同步
  5. 新增测试：非法输入（`"abc"`/未闭合引号/缺冒号）返回 Err
- **验收**：`try_parse` 合法输入返回 `Ok`、非法返回 `Err(JsonError::ParseError)`；现有 `parse` 行为不变；回归全绿。

## P4. `&dyn Error` 上转型（LD#2，中风险，已细化 P4a-1~P4c-2）

- **目标**：支持具体类型 → dyn protocol 对象上转型（`&T as &dyn Protocol` / 自动 coercion）。
- **前置**：无（H4 已有 `let d: dyn Protocol = &obj;` 局部变量主路径；需扩展 `&dyn` 引用上转型）。
- **关键实现点**（此前已探测）：`coerce_to_dyn`（`check_expr/misc.rs`）+ 触发点 `check_stmt.rs:66-78`；根因是 `let d: &dyn Error = r` 注解为 `Type::Ref(Box(Dyn))` 不匹配现有 `Type::Dyn` 分支。

**拆分**（风险从高到低逐项化解）：
- **P4a（核心，中风险）`&T → &dyn Protocol` 引用上转型**：扩展 `check_stmt.rs` 匹配 `Type::Ref(Box(Dyn))`，触发 `coerce_to_dyn`；构造胖指针（data + vtable）引用。验收：`let d: &dyn Error = r`（r: &MyError）编译通过。
- **P4b（中风险）去虚拟化 vtable 槽**：`coerce_to_dyn` 的 3 元 vtable（drop/size/align + N 方法槽）在引用上转型路径正确构造（数据指针指向引用目标、非被引用栈上对象）。验收：`d.source()`/`d.message()` 经 vtable 分派到 MyError 实现。
- **P4c（验证，低风险）Y6 source 链式**：`source() -> Option<&dyn Error>` 构造非 `None` 值，链式 `source` 可遍历。验收：Y6 目标签名完整落地。

- **验收（整体）**：`let d: &dyn Error = r` 编译通过且虚调用正确；Y6 source 链式实现可落地。

## P5. std Mutex 泛型化（LD#6，中风险，已细化 P5a-1~P5d-2）

- **目标**：`Mutex<T>` 从空锁升级为带值锁 + `MutexGuard<T>` 持值访问。
- **前置**：P4（生命周期/借用 MVP 思路）；Y4a/Y4b（泛型构造 + 静态方法推断已齐）。
- **MVP 最小集**：`Mutex<T> { p: i64, value: T }` + `new(v: T)` + `lock_guard()` 返回带 value 指针的守卫 + `get/get_mut`（**裸指针访问，不做 Deref 分派**）。

**拆分**（按可独立验证的粒度）：
- **P5a（中风险）`Mutex<T>` 带值锁 + `new(v)`**：`sync/module.rl` `struct Mutex<T> { p: i64, value: T }` + `impl<T> Mutex<T> { fn new(v: T) }`；`core.rl` import 泛型化。验收：`Mutex::new(42)` 编译，锁原语方法（lock/unlock/try_lock）保持。
- **P5b（中风险）`MutexGuard<T>` 持值访问**：`lock_guard()` 返回守卫并捕获 `&value` 地址（存 i64 裸指针），`get(&self) -> &T`/`get_mut(&mut self) -> &mut T` 经 `__rlyeh_deref`/extern 间接访问。验收：`Mutex::new(42).lock_guard().get()` 取到 42。
- **P5c（中风险）desugar guard 注入确认**：`rlyeh-desugar/src/guard.rs` 按方法名 `lock_guard` 特判（AST 阶段无类型），确认泛型化后注入 `unlock()` 语义不变。验收：guard 块尾自动解锁仍生效。
- **P5d（低风险）测试/示例迁移**：driver `sync_test.rs` `Mutex::new()` → `Mutex::new(载荷)`；`mutex_guard.rl`/06-sync 示例/run-pass 全量迁移。验收：迁移后回归全绿。

- **验收（整体）**：`Mutex::new(42).lock_guard()` 持锁经 `get` 取值；全量迁移后回归全绿。

## P6. 泛型 protocol 实参路径 + where 子句（LD#4，中风险，已细化 P6a-1~P6c-3）

- **目标**：泛型类型实参支持 `::` 路径（`impl From<io::error::IoErrorKind>`）+ 增加 `where` 子句。
- **前置**：无。

**拆分**：
- **P6a（中风险）impl 头泛型实参 `::` 路径**：parser `item.rs` 的 impl 泛型解析——当前类型实参 `parse_type` 已支持 `::` 路径（`ty.rs:69-85` `parse_path_type` 收集 `a::b::c`），但 `impl From<io::error::IoErrorKind>` 仍报 `expected '>', found Colon`——需定位 impl 头解析是否走 `parse_type`（疑似 impl 头特化路径未用完整 `parse_type`）。修复使 impl 泛型实参走完整路径解析。验收：`impl From<io::error::IoErrorKind> for IoError` 可写。
- **P6b（中风险）`where` 子句语法**：parser `item.rs` 增加 `where` 子句解析（`impl<T, U> Into<U> for T where U: From<T>` + 泛型函数 `fn f<T>(..) where T: Bound`）。验收：`where` 子句语法可解析进 AST。
- **P6c（中风险）typecheck where 约束生效**：where 约束在泛型 impl/函数实例化时检查（bound 解析 `item.rs:100-105` 当前仅 `expect_ident` 裸名，需支持 `::` 路径 bound）。验收：blanket impl 实例化时校验 `U: From<T>`；`?` 运算符 From 自动转换前提落地。

- **验收（整体）**：模块路径类型泛型 impl 可写；where 子句 + blanket impl 生效。

## P10. E1 Windows/ARM 交叉编译（LM#6，中风险，已细化 P10a~P10c）

- **目标**：补 Windows arm64 / Linux x86_64 / Linux arm64 交叉编译产物。
- **前置**：工具链（arm64 MinGW 缺失 / zig 与 musl 链接不兼容）/ CI。

**现状障碍**（此前实测）：
- Windows arm64：需 `aarch64-w64-mingw32-gcc` 链接器（brew `mingw-w64` 仅提供 i686/x86_64，无 arm64）
- Linux：zig 0.13 与 Rust `x86_64-unknown-linux-musl` 的 `-static-pie`/`-Bstatic` 链接不兼容；zig 下载不稳定（transfer closed）
- 本机已有：macOS arm64/x86_64、Windows x86_64 产物（toolchains/dist）

**拆分**：
- **P10a（中风险）工具链评估与安装**：评估 3 条路径——(1) arm64 MinGW（GitHub Actions `windows-2025`/交叉 runner 或手动下载 arm64 mingw）；(2) musl-cross（`musl.cc` 预编译交叉工具链，比 zig 更兼容 Rust，但下载亦依赖网络）；(3) 扩展 CI 矩阵让 CI 原生构建。产出：选定各缺失平台的最可靠工具链路径。验收：工具链可稳定下载/配置。
- **P10b（中风险）release.yml CI 矩阵扩展**：release.yml 覆盖缺失平台——Windows arm64（交叉）、Linux x86_64/arm64（原生 runner 或交叉）；复用现有 toolchain 打包逻辑。验收：CI 可构建缺失平台并产出归档。
- **P10c（低风险）产物验证**：各平台归档 bin 完整性（6 工具 + wrapper）+ std/skills/examples 可重定位；加入 release 清单。验收：toolchains/dist 补齐缺失平台。

- **验收（整体）**：缺失平台（Windows arm64 / Linux x86_64 / Linux arm64）toolchain 包产出且验证通过。

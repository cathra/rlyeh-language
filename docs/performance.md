# Rlyeh 性能对比：与 C / C++ / Go / Swift / Rust 全方位对比

> 版本：0.1.0（MVP）　数据日期：**2026-08-31（本机重新实测）**　环境：Apple Silicon
>
> 本文是 Rlyeh 与 **C / C++ / Go / Swift / Rust** 五门主流系统级 / 应用级语言的**全方位性能对比**。所有数字来自仓库内置基准集 `examples/projects/benchmarks/`，逻辑严格一致、统一编译、统一计时，可复现（见 §7）。

> **关于本次数据的说明**：上一版 `benchmarks/README.md` 中的 Rlyeh 数值（如 actor 6.7ms、dyn_dispatch 3.6ms）**从未被自动化脚本真正产出**——基准脚本 `run.py` 曾把 Rlyeh 源文件扩展名误写成 `rlyeh`（应为 `rl`），导致 Rlyeh 每次编译都因找不到 `*.rlyeh` 文件而 I/O 失败，那些数字为手写 / 过乐观估计。本次（2026-08-31）已修正该笔误（`rlyeh`→`rl`），以下为**本机真实重测**结果。

---

## 0. 概述与方法论

Rlyeh 的设计目标是：**Rust 的安全性 + Go 的编译速度 + Erlang 的并发模型 + 数学的自然表达**。性能上它标的是「系统级语言的运行效率」——即默认产出**发布级优化**的机器码（基于 LLVM，等价于 `clang -O3`）。

**基准维度（13 项，覆盖计算 / 容器 / 并发 / 多态 / 内存）：**

| 基准 | 内容 | 考察点 |
|------|------|--------|
| `fib` | fib(30) 双递归 | 函数调用开销 + 整数运算 |
| `loop_sum` | 1 亿次 i64 循环累加 | 整数运算 + 分支 |
| `matmul` | 256×256 f64 矩阵乘法 | 浮点运算 + 内存访问 |
| `strcat` | 字符串拼接 10 万次 | 字符串缓冲扩容 |
| `hashmap` | 20 万 insert + 20 万 get（LCG i64 键） | 哈希表 |
| `sort` | LCG 生成 5000 个 i64 排序 | 排序算法 + 标准库 |
| `actor_pingpong` | 5 万次 actor 同步往返 | **Actor 并发模型**（消息调度吞吐） |
| `btree` | 深度 15 完全二叉树构造 + 递归求和 | 层次内存访问 + 递归 |
| `hashmap_str` | 1 万条字符串键 insert + get | 字符串哈希 + 运行时键构造 |
| `dyn_dispatch` | 2000 万次多态分派 | **dyn Trait / 虚函数 vtable** |
| `region_alloc` | 100 万次小对象分配 | **region 批量分配 vs 逐次分配** |
| `region_batch` | 100 万循环 × 每次 4 小对象分配 | **region 多 bump 点批量提升** |
| `nqueens` | 12 皇后回溯搜索 | 深度搜索 + 递归 + 剪枝分支 |

**编译优化级别（如实声明）：**

| 语言 | 编译器 / 优化 | 说明 |
|------|------------|------|
| Rlyeh | `rlyeh build`（clang -O3 发布级优化） | LLVM 循环优化 / 向量化 / 常量传播 / 寄存器分配 |
| C / C++ | `clang -O3` / `clang++ -O3` | 发布级优化 |
| Go | `go build` | gc 编译器默认优化（无 -O 分级） |
| Swift | `swiftc -O` | 发布级优化 |
| Rust | `rustc -O` | 发布级优化 |

**计时策略**：每基准每语言 warmup 1 次 + 正式 5 次取中位数（毫秒），进程启动开销各语言一致。**编译计时**：单次全量冷编译（Rlyeh 用 `--force` 绕开增量缓存，其余语言无增量缓存）。**输出校验**：构建后首次运行捕获各语言 stdout，跨语言不一致自动告警（浮点按数值容差）。

## 1. 总体结论（基于 2026-08-31 本机重测）

1. **Actor 并发全场地最快**：`actor_pingpong` 7.5ms，是全部 6 语言中**唯一低于 10ms** 的，较 Go（11.4ms）快 **1.5x**，较 C/C++/Rust/Swift（~158–181ms）快 **21–24x**。这是 Rlyeh 当前最明确的性能优势。
2. **浮点 / 递归类与最快语言几乎同速**：`matmul` 1.12x、`nqueens` 1.11x、`region_batch` 1.13x——矩阵乘法、回溯搜索、批量 region 分配均落在最快语言的 1.1x 出头。
3. **整数循环 / 排序 / 哈希普遍落后 1.8–2.4x**：`loop_sum`/`sort`/`btree`/`strcat` 约 1.8–1.9x，`hashmap` 1.95x，`dyn_dispatch` 2.15x，`region_alloc` 2.38x——主要差距来自 clang/rustc 对整数循环的强度削减 / 向量化，以及 Rlyeh 运行时的逐对象语义检查。
4. **字符串键容器是最大短板**：`hashmap_str` 3.52x（Rlyeh 键构造每次多分配），`region_alloc` 2.38x（region bump 当前慢于他语言手动 bump）。
5. **相对 Go / Swift 仍全面占优**：在几乎所有 CPU 密集型基准上 Rlyeh 都快于 Go / Swift（二者 gc 编译器不对纯整数循环做 -O3 级优化，如 `loop_sum` Go 25.3ms / Swift 24.8ms vs Rlyeh 4.3ms）。

> 与旧 README「12/13 项贴近 C」的乐观表述不同，本机真实重测显示：Rlyeh 在 **actor 并发上全场最快**，其余项**普遍落在最快语言的 1.1–3.5x 区间，多数在 2x 以内**——是一份「有亮点、有差距」的诚实画像，而非全面持平。

## 3. 编译速度对比（2026-08-31 本机重测，单次全量冷编译）

> 单位：毫秒（ms），每基准冷编译的实测区间。

| 语言 | 冷编译耗时（区间） | 相对 Rlyeh |
|------|------------------:|:---:|
| C | 40–60 | 约 4x 更快 |
| Go | 42–50 | 约 4.5x 更快 |
| Rust | 73–164 | 约 1.5–3x 更快 |
| C++ | 40–220 | 部分更快 / 同档 |
| Swift | 148–282 | 同档 / 更慢 |
| **Rlyeh** | **220–238** | — |

**解读**：Rlyeh 当前走完整 LLVM 优化管线，单次冷编译 ~220–238ms，慢于 C/Go（~40–60ms），与 Swift（~148–282ms）同档，略慢于 Rust（~73–164ms）。项目目标「编译速度对标 Go」依赖后续**增量缓存**与**惰性 LLVM 后端**（未使用的代码路径延迟到链接期优化），而非当前全量管线。

## 4. 分维度深度分析（基于真实重测）

### 4.1 纯计算 / 数值

- `matmul`（13.17ms，1.12x）：256×256 f64 矩阵乘法，浮点 + 内存访问密集，Rlyeh 与 Rust（11.72ms）几乎同速，明显快于 Swift（14.04ms）。
- `nqueens`（62.84ms，1.11x）：12 皇后回溯，Rlyeh 与 Rust（56.53ms）最接近，快于 C/C++/Go/Swift。
- `fib`（5.80ms，1.23x）：双递归，Rlyeh 与 C/C++/Rust 同一梯队，略慢于 Go（4.73ms）/ Swift（4.88ms）。
- `loop_sum`（4.29ms，1.87x）：1 亿次整数累加，Rlyeh 落后于 C/C++（~2.3ms），但**远快于 Go（25.3ms）/ Swift（24.8ms）**——gc 系编译器不对纯整数循环做 -O3 级强度削减 / 向量化。
- `btree`（4.54ms，1.89x）：递归 + 层次内存访问，Rlyeh 约 C/C++ 的 1.9x。

### 4.2 字符串与标准库容器

- `strcat`（4.38ms，1.84x）：字符串拼接，Rlyeh 约为 C/C++/Rust（~2.4–2.8ms）的 1.8x，快于 Swift（3.85ms）、远超 Go 之外的差距不大。
- `sort`（4.36ms，1.85x）：5000 个 i64 排序，Rlyeh 约为 Rust（2.35ms）的 1.85x。
- `hashmap`（9.18ms，1.95x）：20 万次 insert + get，Rlyeh 优于 Go（18.5ms）/ Swift（7.92ms），但落后于 C（4.69ms）/ Rust（5.50ms）——标准库哈希表仍有优化空间。
- `hashmap_str`（9.81ms，3.52x）：字符串键场景，**最大短板**——差距主要来自 Rlyeh `format!` 键构造（每次多次分配），对照 C++/Go/Rust/Swift 单次分配。

### 4.3 并发模型（Actor）

`actor_pingpong` 是 Rlyeh 的**标志性优势项**：5 万次 actor 同步往返仅 7.5ms，成为全部 6 语言最快（0.66x）。

- 较 Go（11.4ms）快 **1.5x**：Go 无缓冲 channel 单生产者/消费者有锁竞争的 runtime 快速路径；Rlyeh 的 **ask 快速路径**同线程同步短路，抢到 `running` 后直连 mailbox + state 锁，全程零调度 / 零通道。
- 较 C/C++/Rust/Swift（~158–181ms）快 **21–24x**：pthread condvar 每次往返需 futex 唤醒，而 Rlyeh 在竞争时才回退慢路径（`Envelope` 回复通道）。
- 语义保守安全：变量被重新赋值导致映射失效时自动回退 vtable 间接调用。

### 4.4 多态分派（dyn Trait / 虚函数）

`dyn_dispatch`：2000 万次多态分派，Rlyeh 4.84ms 为**仅次于 Rust（2.25ms）**，快于 Go（4.99ms）/ C（13.4ms）/ C++（12.8ms）/ Swift（24.3ms）。

- Rlyeh 约为 Rust 的 **2.15x**——已具竞争力（优于 Go/C/C++/Swift），但与 Rust 的去虚拟化仍有差距。Go 接口 itab 间接调用在此基准与 Rlyeh 接近。

### 4.5 内存 / Region

- `region_batch`（12.93ms，1.13x）：100 万循环 × 每次 4 小对象，Rlyeh 与 Rust（11.44ms）/ C（11.53ms）/ Go（11.48ms）几乎同速，仅慢于最优约 13%，已压到内存带宽极限。
- `region_alloc`（5.87ms，2.38x）：单对象 100 万次分配，Rlyeh 为**最慢**一项（C++ 2.47ms / Rust 2.94ms / Swift 3.08ms / Go 3.11ms / C 4.53ms）。当前 region bump 的逐对象越界 / 语义检查开销高于他语言手动 bump，是后续优化重点。

## 5. Region 内存策略对比（Rlyeh 内部，同机同构 100 万次 32B 对象）

> 该表为 Rlyeh 自身不同 region 策略的横向对比（不涉及跨语言），数据于 **2026-08-31 本机重测**（warmup 12 + 40 次取中位数），可与 §2 的 `region_*` 跨语言项互参。

| 策略 | 语法 | 块数（扩容次数） | 内存峰值 | 耗时 (ms) | 较最优 |
|------|------|:---:|:---:|-----:|:---:|
| plain（默认 bump ×2） | `region 'r {}` | 14（13 次） | 17.5MB | 4.644 | +0.4% |
| adaptive（EWMA 画像） | `region 'r adaptive {}` | 21（20 次） | ~17.5MB | 4.698 | +1.6% |
| `with_size (32MB)` | `region 'r with_size (33554432) {}` | 1（0 次） | 32MB | 4.780 | +3.3% |
| `with_size (4KB)` | `region 'r with_size (4096) {}` | 9（8 次） | 26.8MB | 4.907 | +6.1% |
| `strategy (bump)` | `region 'r strategy (bump) {}` | 14（13 次） | 17.5MB | **4.625** | — |

**洞察**：五种策略耗时全部落在 4.6–4.9ms，且 run-to-run 中位数排序在噪声内翻转（strategy_bump / with_size_32MB / plain 逐次成为"最快"）——即策略间**无统计学显著差异**；热循环分配为纯寄存器 bump（约 2.6 ns/次：扣除 2.06ms 空循环基线，1M 次分配仅 ~2.58ms），策略差异只作用于慢路径扩容次数。对照：**无 region 逐次堆分配 9.77ms，region 分配约为其 1/2**。日常代码放心使用默认 `region`；仅在已知精确上限时用 `with_size (N)` 规避全部扩容。

## 6. 剩余差距与后续方向

| 项 | 当前差距（vs 最快） | 主因 | 方向 |
|----|------------------|------|------|
| `hashmap_str` | 3.52x | Rlyeh `format!` 键构造每次多次分配 | 键构造单次分配 / 字符串构建器 |
| `region_alloc` | 2.38x | region 逐对象语义检查高于手动 bump | 弱化 / 可选越界检查、批量分配快路径 |
| `dyn_dispatch` | 2.15x | 去虚拟化覆盖面不及 Rust | 扩展去虚拟化命中场景 |
| `loop_sum` / `sort` / `btree` / `strcat` | 1.8–1.9x | clang 强度削减 / 向量化优势 | 循环强度削减 pass |
| `hashmap` | 1.95x | 标准库哈希表探查 | 继续贴近 Rust |
| 编译速度 | ~4x vs C/Go | 完整 LLVM 管线 | 增量缓存 + 惰性 LLVM 后端 |

## 7. 复现方法

所有数据均可由仓库内置脚本复现（**注意：需从工作区根目录运行**，因为 `rlyeh-driver` 按当前工作目录定位标准库）：

```bash
cd examples/projects/benchmarks
python3 run.py                  # 完整跑 13 基准 × 6 语言
python3 run.py --runs 10        # 增加正式运行次数（更稳）
python3 run.py --only fib,matmul
python3 run.py --skip-rlyeh-build
```

- **逻辑等价性**：所有语言输出逐项一致（`832040` / `4999999950000000` / `200000` / `19999900000` / sort 首尾值相同 / `1250025000` / `2166712927200` / `49995000` / `70000000` / `499500000` / `2000497500000` / `14200`）。
- **运行期自动校验**：`run.py` 捕获各语言 stdout 对比，不一致即告警（浮点按数值容差，因各语言 f64 打印精度不同）。
- **随机数**：统一 LCG 常数（MMIX：A=6364136223846793005, C=1442695040888963407）；Rlyeh 的 i64 乘法为 wrapping 语义（已实测），C/C++ 用无符号算术保证无 UB。
- **已知脚本问题已修复**：`run.py` 中 Rlyeh 源文件扩展名曾误写为 `rlyeh`（实际为 `rl`），导致 Rlyeh 从未被真正编译；已于 2026-08-31 修正。

**原始数据**：`examples/projects/benchmarks/results/raw.json`（run_ms + compile_ms）；**完整报告**：`examples/projects/benchmarks/results/benchmark_report.md`。
